# Deploying this to the live hospital server

## What the push did and did not do

Pushing to `main` did **not** touch the live server. Both deploy workflows ran their
`test` job and then **skipped** the deploy job, because the repo variables that gate them
(`EC2_DEPLOY_ENABLED`, `AWS_DEPLOY_ENABLED`) are not set. Live is therefore still on the
previous build until someone deploys deliberately. CI (typecheck, lint, full production
build) passed on the merged commit.

## Order matters: migrate BEFORE the new code serves traffic

This release adds columns that the new code reads. Deploying the code **without** applying
the migration will break the Deposits and Refunds screens, because Prisma selects every
column declared in the schema and Postgres will reject the missing ones.

This is not hypothetical — `EOD_2026-06-09.md` records the same failure: *"live server was
serving a stale .next build and the RDS DB was missing migrations the code required."*

The safe order (which the EC2 workflow already follows) is:

```
git pull origin main
npm ci --no-audit --no-fund
npx prisma generate
npx prisma migrate deploy      # ← must succeed before the reload
npm run build
pm2 reload ecosystem.config.js --update-env
```

Sanity-check before and after:

```
npx prisma migrate status      # should list 20260722000000_add_refund_mode as pending, then applied
```

The migration is safe to run against live data:

- Five `ALTER TABLE ... ADD COLUMN`, all **nullable, no default, no index, no constraint**.
  On Postgres 11+ this is a metadata-only change — no table rewrite, no row scan.
- Every statement uses `IF NOT EXISTS`, so it is idempotent and re-runnable.
- Nothing is dropped, renamed, backfilled or modified. Existing rows are untouched.
- Rollback, if ever needed, is simply dropping the five columns; no data is lost by leaving
  them in place.

Two migrations from the TPA work (`20260721000000`, `20260721010000`) are also pending on
live if they haven't been deployed yet. They are likewise additive, though
`20260721010000` adds a foreign key on `ipd_packages`, which takes a brief validation lock
— trivial on a table that size, but it is the one statement worth watching.

## Avoiding the deploy-time overload

The overload is caused by the deploy itself, not by the push. `npm run build` runs **on the
production box** with a 4 GB heap and spawns a worker per core for static generation (this
release: 320 pages, 15 workers locally). On a small instance, that competes directly with
the PM2 cluster serving patients, and the site becomes unresponsive.

Mitigations, cheapest first:

1. **Deploy in a low-traffic window.** Simplest and most effective.
2. **De-prioritise the build** so PM2 keeps the CPU it needs:
   `nice -n 19 npm run build`
3. **Cap static-generation parallelism** rather than letting it use every core, e.g.
   `experimental.cpus` in `next.config.ts`, or deploy on an instance with headroom.
4. **Build off-box.** The real fix: build the artifact in CI (or as a Docker image, which
   `deploy-aws.yml` already does) and ship the result, so the production server only pulls
   and reloads. This removes build load from the hospital's server permanently.

`pm2 reload` itself is a rolling restart and is not the problem — it keeps workers serving
while they cycle. Keep the existing post-deploy `curl -sf http://localhost:3000/api/health`
gate so a bad deploy is caught immediately.

## If something looks wrong after deploying

Nothing in this release migrates or rewrites existing data, so a rollback is a code
rollback only:

```
git checkout <previous-commit> && npm ci && npm run build && pm2 reload ecosystem.config.js
```

The five added columns can stay — the previous build simply ignores them.
